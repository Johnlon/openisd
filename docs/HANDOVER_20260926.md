## Advice, in the order it will save you time

**Run heavy work through the funnel.** `~/.claude/bin/heavy.sh npm run typecheck`, and the same
for vitest, playwright and any build. Four lanes share one cgroup, `heavy.slice`, capped at 800%
CPU and 6 G memory with swap off. `/home/john/bin/npm` and `npx` are PATH shims that route heavy
subcommands through it automatically, so you often get this without asking. The point is that N
sessions cannot multiply the ceiling.

**A test that fails under load is not necessarily flaky.** Two things produced convincing
imitations of flakiness here in one day, and both were deterministic once found:

- A bare `npx playwright test <file>` used to default to port 4100, inside the pool
  `scripts/test-concurrency.sh` hands out under a lock, and its `webServer` command opens with
  `kill-http.sh <PORT>`. Starting a targeted run killed a full gate's server mid-suite, and that
  gate failed on whatever it happened to be doing. Fixed, but the shape recurs: before believing
  "flaky", ask what else on the box could be touching the same resource.
- `load_guard.sh` killed on load average. It fired eight times with 10–12 GB free and took out
  two commits and a push. It now triggers on available memory only; the load figure is logged
  and never acts. If you find yourself raising a threshold to get work through, you are probably
  measuring the wrong thing.

**Before re-pinning a number that a change moved, find out where the number came from.**
Re-pinning is how a real parity difference gets buried. `CEILING_HZ` in
`packages/ui/test/logic/vent-target-reachability.test.ts` moved 4 ppm and was safe to re-pin — it
is OpenISD's own computed output, not a WinISD capture, and 4 ppm is exactly the documented
speed-of-sound difference between the two air models. A number traced to a `.wpr` golden gets the
opposite treatment: the difference is the finding.

**And the inverse: a slack tolerance hides what it was meant to document.** Two `Fr` assertions
carried 0.05 Hz with comments saying the slack existed to record an air-model gap honestly. It
recorded the gap and then let it persist for weeks. When the gap closed the error was 6e-14 Hz.
If you write a tolerance to document a known defect, the defect needs a bug record with the
measurement in it, and the tolerance needs tightening the day it is fixed — otherwise nothing
tells you it was.

**When a test contradicts the app, suspect the test — but prove it.** The drag-select test had
never passed, at any commit, including the squash that introduced it. It was wrong twice: it
started the drag on the Y-axis strip (the level pan/zoom control, so no band was ever created),
and it counted a dark run over 20% of the plot width when the curve is drawn on top of its own
level line and leaves less. Proving the app innocent took temporary `console.log` in
`onPointerDown`, `onPointerMove` and `redraw()`, and a throwaway spec logging what the canvas
actually receives. That is the cheap way in: log what the DOM sees before theorising.

**Check with the other sessions before touching a shared file.** Several sessions work this tree
at once. A one-line message naming the file saves an hour of conflicting edits, and the answer is
usually "it's free". Uncommitted changes you did not make are someone's live work.

**The oracle is WinISD, not our code.** Only a `.wpr`/`.wdr` capture, a debugger reading, a
decompile or the help files settle what WinISD does. OpenISD's own output never does, however
confident it looks — and neither does a previous agent's summary of what WinISD does.

## Open, and what I would do next

- `BUG_20260926_drag-select-draws-one-level-line-not-two.md` is RESOLVED, but the investigation
  turned up something nobody has looked at: a drag that STARTS in the Y-axis gutter silently
  becomes a level pan. That may be right, or it may be a user trap. Unexamined.
- The parity doc's WinISD Compatibility table is now the reliable summary of what each switch
  does: `docs/research/WINISD_PARITY.md`. Read it before touching a compat flag.
- Per the README goal, every control the two apps share must behave like WinISD by DEFAULT, with
  conventional behaviour behind a switch. `useWinisdDriverModel` was the wrong way round until
  today. Others may be too — that is a sweep nobody has done.

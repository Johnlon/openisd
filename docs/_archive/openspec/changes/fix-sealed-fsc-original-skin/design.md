## Context

See `proposal.md` - Why for the full root-cause trace (live-reproduced, file:line cited). In
short: `OriginalShell.vue`'s sealed-box `Fsc`/`Qtc` (and, via the same computed property, the
bandpass4 rear-chamber "Frc") is wired to `findImpedancePeak` (`packages/engine/src/alignments.ts:131`),
an impedance-curve global-argmax estimator that degenerates to `{ Fsc: fmax, Qtc: 0 }`
whenever a driver's high-frequency inductive impedance rise exceeds its low-frequency
resonance bump — which is common, not an edge case. `StatBar.vue`/`ModernShell` already use
the correct, WinISD-bit-exact `sealedResonance()` (`packages/engine/src/lossMode.ts`, added by
commit `9ffa0d2`, unmodified by this change). `wprMapping.ts`'s `.wpr` export shares the same
defect via the same `findImpedancePeak` call.

## Goals / Non-Goals

**Goals:**
- Every skin's sealed-box `Fsc`/`Qtc` — and the `.wpr` export's `Fr` for sealed/bandpass4 —
  comes from the one canonical `sealedResonance()` calculation, with no independent estimator
  that can silently diverge or degenerate.
- A golden functional test pins `sealedResonance(WinisdLossy, ...)` against an
  independently-generated oracle value for a real driver (Dayton Audio E150HE-44), not just
  the existing synthetic reference-driver grid in `loss-mode.test.ts`.
- Remove the now-dead `findImpedancePeak`/`sealedFc` rather than leave a broken, unused
  duplicate of the canonical model sitting in the engine.

**Non-Goals:**
- Not reproducing WinISD's own *derived* driver `Qts` (the `Re_eff`/`alfaVC` voice-coil-
  resistance correction documented in `../winisd_research/SEALED_FSC_MODEL.md` §5). That is
  explicitly scoped there as "a separate driver-solver task" — this change's golden test uses
  the E150HE-44's nominal, stored `Qts=0.39`, with a tolerance band wide enough to cover that
  known, documented, unmeasured-for-this-driver gap (Decision 3).
- Not consolidating the *other* two duplicate lossless-formula implementations this
  investigation surfaced (`alignments.ts`'s `sealedFc` — deleted here because it becomes
  unused, not because of the duplication — and the inline `d.Fs * Math.sqrt(1 + d.Vas /
  state.P.Vb)` fallback already present in `OriginalShell.vue`'s `rearResonance`/`rearQtc`,
  which this change also removes as part of replacing those two computed properties). No
  other lossless-formula duplicate is touched.
- Not changing `packages/engine/src/lossMode.ts`'s formulas — confirmed correct by direct
  probing (see proposal.md - Impact).

## Decisions

**1. Fix by replacing the estimator, not by patching `findImpedancePeak`'s boundary case.**
`findImpedancePeak` could be patched (e.g., restrict the argmax search to frequencies below
some multiple of `Fs`, or detect the boundary case and fall back to the lossless formula) —
but the project already has a validated, bit-exact-to-WinISD model for exactly this quantity
(`sealedResonance()`), used correctly by two of three skins. Patching the impedance-peak
estimator would leave TWO independently-maintained implementations of "sealed-box Fsc/Qtc"
that can still diverge on some other input the patch didn't anticipate — the actual failure
mode here. Routing every consumer through the one canonical function removes the divergence
risk structurally, not just for the specific inputs reproduced. This mirrors the workspace's
"one model, one shape" posture applied to a calculation rather than a data record.

**2. Delete `findImpedancePeak`/`sealedFc` once both consumers migrate, rather than leave them.**
Confirmed (grep, proposal.md - Impact) that `wprMapping.ts` and `OriginalShell.vue` are their
only production consumers. After both switch to `sealedResonance()`, the functions are dead
code implementing a broken duplicate of a now-superseded model — keeping them invites a future
regression where a new call site reaches for the wrong one. `alignments.test.ts`'s
`findImpedancePeak` describe block is deleted with it (it tests a function that no longer
exists); the file's other, unrelated describe blocks (EBP, `sealedFromQtc`, vented alignment,
port length/tuning, PR tuning) are untouched.

**3. Golden E150HE-44 test tolerance: generated from the research oracle, nominal Qts, ±0.5 Hz / ±0.02 Qtc.**
Golden values are generated by importing `../winisd_research/lib/winisd_resonance.py`
directly (not hand-transcribed) at the E150HE-44's actual `Fs=40, Vas=0.007645536, Qts=0.39`
and openisd's own default box losses `Ql=10, Qa=100`, giving `Fsc≈63.208 Hz, Qtc≈0.592`
(computed during this investigation; the task list re-generates and records the exact digits
when the test is written). The tolerance is set wider than `SEALED_FSC_MODEL.md`'s documented
~0.03 Hz gap for its own reference driver, because that gap's magnitude is driver-specific
(it scales with how far nominal `Qts` sits from WinISD's derived `Qts`) and has not been
separately measured for the E150HE-44 — asserting tighter than that would be asserting false
precision. Alternative considered: use the pure lossless case (`Ql=Qa=∞`) instead, whose `Fsc`
(60.3225 Hz) happens to match the user's recalled "~60.32 Hz" almost exactly — rejected as the
primary golden case because openisd's actual default box is NOT lossless (`Ql=10, Qa=100`),
so a lossless golden test would not catch a regression in the lossy cubic path, which is the
code actually being fixed. The lossless value is still useful as a documented cross-check
(Decision 4).

**4. Keep the lossless case as a secondary, exact-match golden point.**
Unlike the lossy case, the lossless formula (`fs·√(1+Vas/Vb)`) does not depend on `Qts` at all,
so it can be asserted exactly (no tolerance) for the same driver/box — a second, independent
data point on the same fixture at negligible extra cost, and a useful sanity anchor given it
matches the user's own recollection almost exactly.

## Risks / Trade-offs

- **[Risk] Switching `OriginalShell.vue`'s bandpass4 "Frc" field (which reuses `rearResonance`)
  changes its computed value too, not just the sealed-box case.** → Mitigation: this is
  intentional and correct — `wprMapping.ts`'s own comment already documents that bandpass4's
  rear chamber "is SEALED — driver's own chamber, same formula as `sealed`", so both must move
  together to stay consistent; `tasks.md` includes verifying the bandpass4 case explicitly,
  not just plain sealed.
- **[Risk] The `.wpr` export's `Fr` value for sealed/bandpass4 boxes changes for any project
  where the old estimator wasn't degenerate but still differed from the correct cubic value.**
  → Accepted: the old value was never correct (it was, at best, an impedance-curve
  approximation of the same quantity `sealedResonance()` computes exactly); exporting the
  correct value is the intended fix, not a side effect to guard against.
- **[Trade-off] This change touches `core-engine`'s spec, not just `ui-presentation`'s** — see
  proposal.md - Capabilities. Flagged explicitly rather than silently narrowing the delta to
  avoid the extra file, because leaving the contradictory scenario in place would mean
  `openspec validate`'s traceability could point a future reader at `alignments.test.ts` for a
  scenario that file no longer covers. `openspec validate --strict` requires a MODIFIED
  requirement to retain every existing scenario NAME (archive replaces the whole block), so
  the delta keeps the "Lossy system resonance (Fsc) and Q (Qtc) sealed peak tracking" scenario
  and rewrites its content to state the delegation, rather than deleting it outright.

# Created docs/plans/PLAN_DRIVER_SOLVE_AND_SWEEP_DIAGNOSTICS.md
# Driver Solve and Sweep Diagnostics

Status: PLAN — not implemented

## Goal

Make calculation results explain both successful values and unavailable outputs without mixing
intrinsic driver data-quality issues with sweep/chart failures.

The solver owns driver relations and their dependencies. The sweep owns circuit and curve
diagnostics. The domain projects the two channels separately onto driver cells and chart state.

## Ownership

### `packages/design/engine/solver.ts`

Owns:

- Driver relation definitions and route precedence.
- Solved driver quantities.
- Missing dependencies for an unavailable driver quantity.
- Contradictions between entered driver values.
- All alternative routes to the same target quantity.

It must not calculate UI messages, mutate records, or decide how a DQ is displayed.

### `packages/design/engine/air.ts`

Owns:

- Temperature/humidity/pressure to `rho` and `c`.
- Physical versus WinISD air-model formulas.
- Air defaults and supported ranges.

Air resolution is a calculation dependency, not an intrinsic driver DQ. The solver consumes
resolved air values; it does not read project state or reimplement air formulas.

### `packages/design/engine/sweep.ts`

Owns:

- Circuit execution and frequency samples.
- Box/topology prerequisites.
- Non-finite curve samples and frequency gaps.
- Curve-specific failures such as unavailable maximum-SPL or maximum-power curves.

It must not copy intrinsic driver DQ issues into its sweep error list.

### `packages/design/engine/Engine.ts`

Exposes the public façade for the solver, air, and sweep contracts. It contains no second copy of
the relation or diagnostic logic.

### `packages/design/domain`

Passes entered driver values to the engine and projects returned driver diagnostics onto `Cell`
DQ/provenance state. It projects sweep diagnostics into the project/chart issue channel. It does
not rediscover missing dependencies or compare formulas itself.

### UI hooks

Format the already-typed channels for the interface:

- Driver DQ markers and tooltips come from driver diagnostics.
- Chart/sweep warnings come from sweep diagnostics.
- A sweep may point to missing driver fields, but it does not become the owner of those DQ marks.

## Result Contracts

The exact names may be refined during implementation, but the shape must preserve the distinction.

### Driver solve

```ts
interface DriverSolveResult {
  readonly values: DriverSolverQuantities;
  readonly issues: readonly DriverIssue[];
}
```

`values` may be partial. Missing values are explained by `issues`, not inferred later from an
undefined property.

### Driver issues

```ts
type DriverIssue =
  | {
      readonly kind: 'missing-dependencies';
      readonly target: DriverQuantityName;
      readonly routes: readonly SolveRoute[];
    }
  | {
      readonly kind: 'inconsistent-inputs';
      readonly target: DriverQuantityName;
      readonly fields: readonly DriverQuantityName[];
      readonly formula: string;
      readonly expected: number;
      readonly actual: number;
      readonly relative: number;
    };

interface SolveRoute {
  readonly formula: string;
  readonly required: readonly DriverQuantityName[];
  readonly missing: readonly DriverQuantityName[];
}
```

`DriverQuantityName` must be a concrete engine-owned vocabulary, not arbitrary UI strings.

### Multiple routes

Each target quantity retains all of its known routes.

Example: `Cms` has routes:

```text
Cms <- Vas + Sd + air
Cms <- Fs + Mms
```

Rules:

- If one route is complete, solve the target and return no missing-dependency issue.
- If no route is complete, return one issue containing every route and each route's missing fields.
- If multiple complete routes disagree, return an inconsistency issue describing the competing
  entered fields and the selected route precedence.
- If multiple complete routes agree, return the solved value without an issue.

This makes an unavailable output actionable without making the caller reverse-engineer the
relation graph.

### Sweep result

```ts
interface SweepCalculationResult {
  readonly curves: SweepResult | null;
  readonly issues: readonly SweepIssue[];
  readonly driverPrerequisites: readonly DriverPrerequisite[];
}
```

`issues` contains only sweep/circuit/box failures. `driverPrerequisites` is a separate reference
channel for outputs blocked by missing driver quantities.

```ts
interface DriverPrerequisite {
  readonly output: SweepOutputName;
  readonly missing: readonly DriverQuantityName[];
}
```

Example:

```text
output: maximum SPL
missing: Pe or Xmax
```

The chart can say “Maximum SPL cannot be calculated — see Driver inputs: Pe or Xmax” without
turning that message into a second driver DQ source.

## TDD Sequence

### Engine tests first

- A complete driver returns values and no driver issues.
- A missing single-route input reports the target and exact missing fields.
- A target with multiple routes reports all blocked routes.
- A complete competing route reports an inconsistency with formula, fields, expected, actual, and
  relative disagreement.
- Route precedence matches the WinISD-verified order.
- Rounded values within their recorded precision do not produce false DQ.
- A calculated value is never treated as an entered input on the next solve.

### Domain tests

- Entered fields become the solver input bag.
- Returned driver issues attach to every affected `Cell` in the relation group.
- Calculated/read-only fields receive the issue as symptoms only where the current DQ policy
  requires it.
- No driver issue is emitted for a missing quantity that is not relevant to the requested group.

### Sweep tests

- Missing driver prerequisites are returned separately from sweep issues.
- Invalid box/vent/PR parameters remain sweep issues.
- Non-finite frequency samples identify their series and frequency.
- Maximum-SPL/power failures identify their driver prerequisites without duplicating driver DQ.

### Browser tests

- Driver DQ markers and tooltips use the driver issue channel.
- Chart failures use the sweep issue channel.
- A blocked chart points to the missing driver fields without rendering a second conflicting DQ
  explanation.

- Do not merge driver DQ and chart errors into one untyped string list.
- Do not add compatibility wrappers around the empty `checkConsistency()` method after the unified
  result contract lands; migrate callers to the authoritative result.

# Driver Solve and Sweep Diagnostics

Status: PLAN — not implemented

## Logical Design

### The Calculation Graph

The application has one dependency graph, with four distinct input domains:

```text
entered driver values ──┐
                         ├─> driver solver ──> solved driver values
air/environment values ──┘                         │
                                                   │
box values ───────────────> box solver ────────────┤
                                                   ├─> sweep/circuit ──> curves
signal values ────────────> signal resolver ───────┘
```

Each calculation node has two outputs:

```text
value output       what could be calculated
diagnostic output  why another value could not be calculated, or what contradicts it
```

Diagnostics are part of the calculation result. They are not reconstructed later by the caller
from `undefined`, `null`, `NaN`, or a failed chart.

### Ownership Invariants

1. A formula has one owner: the engine module that implements it.
2. A dependency list has one owner: the calculation node that knows the formula.
3. A diagnostic names the output it explains and the exact dependencies involved.
4. A downstream calculation may reference an upstream diagnostic, but may not clone or reinterpret
   it.
5. Provenance (`entered`, `calculated`, `not-available`) is assigned by the domain because only
   the domain owns the record and knows which values were stated.
6. UI code formats diagnostics; it never decides whether a value is missing, inconsistent, or
   non-finite.

These rules prevent the current accidental split where `solver.ts` derives values, `sweep.ts`
probes possible unblockers independently, and `OpenISDDriver.checkConsistency()` has no real
implementation.

### Route Resolution

Every derived quantity is represented by one or more routes:

```text
target quantity
  ├─ route A: required inputs -> formula
  ├─ route B: required inputs -> formula
  └─ route C: required inputs -> formula
```

For each route the solver computes:

```text
required: all inputs for the route
missing:  required inputs not currently available
```

The target result follows this logic:

```text
complete route exists
  -> calculate using the declared precedence
  -> reporncy only if competing complete routes disagree

no complete route exists
  -> leave target unavailable
  -> return every blocked route and its missing inputs
```

Example:

```text
Cms
  route geometry: Vas + Sd + rho + c
  route mechanics: Fs + Mms
```

If both routes are blocked, the caller receives both explanations. If geometry is complete, the
solver does not make the caller guess that `Cms` could also come from `Fs`/`Mms`.

### Diagnostic Domains

The diagnostic union is partitioned by owner, not by where the failure happened to be observed:

```text
DriverIssue
  missing/inconsistent driver quantities

BoxIssue
  missing/inconsistent Vb, Vf, Fb, vent geometry, PR mass/tuning, or topology fields

SignalIssue
  missing/inconsistent power, voltage, Re, or series-resistance inputs

EnvironmentIssue
  invalid or unavailable temperature, humidity, pressure, or air-model inputs

SweepIssue
  circuit singularity, non-finite sample, empty curve, unsupported simulation output
```

The owner is determined by the input domain, not by the consumer. For example, a missing `Pe`
reported while calculating maximum SPL is still a driver prerequisite; it is not a new generic
sweep DQ. A zero vent area found while sweeping is still a box issue; the chart may report that it
is blocked by the box issue, but it does not become the box issue's second owner.

### Result Contract

The public calculation result carries value and diagnostics together, while keeping domains
typed:

```ts
interface DriverSolveResult {
  readonly values: DriverSolverQuantities;
  readonly issues: readonly DriverIssue[];
}

interface SweepCalculationResult {
  readonly curves: SweepResult | null;
  readonly issues: readonly SweepIssue[];
  readonly driverPrerequisites: readonly DriverPrerequisite[];
  readonly boxPrerequisites: readonly BoxPrerequisite[];
  readonly signalPrerequisites: readonly SignalPrerequisite[];
  readonly environmentPrerequisites: readonly EnvironmentPrerequisite[];
  readonly configurationPrerequisites: readonly ConfigurationPrerequisite[];
}
```

The prerequisite arrays are references, not duplicated DQ records. They let the chart explain
why it is unavailable while the owning domain places the actionable DQ beside the responsible
field.

### Module Boundaries

```text
air.ts
  environment inputs -> Air { rho, c }
  no driver relations, no box logic, no UI diagnostics

solver.ts
  driver input graph -> DriverSolveResult
  no circuit traversal, no chart concepts, no record mutation

circuit.ts
  one frequency + complete circuit inputs -> one Solution
  no dependency discovery and no UI-facing DQ

sweep.ts
  resolved driver/box/signal/air inputs -> SweepCalculationResult
  no duplicated driver relation graph

Engine.ts
  public façade over the above modules

domain
  live record + engine result -> Cells/provenance/domain issue channels

UI hooks
  domain issue channels -> user-facing text, markers, and chart notices
```

`circuit.ts` is deliberately lower-level than `solver.ts`: it assumes its required quantities
exist and solves the hysical network. `solver.ts` is the dependency resolver that makes those
quantities available or explains why it cannot. `Engine.ts` is neither a third solver nor a place
for formulas; it is the only public door.

## Goal

Make calculation results explain both successful values and unavailable outputs without mixing
intrinsic driver, box, environment, and sweep/chart issues.

# Calculation and Diagnostic Contract

Status: PLAN — not implemented

## Terms

| Term | Meaning |
|---|---|
| **Solver** | Derives missing quantities from known quantities and reports why a target cannot be derived. It does not draw curves. |
| **Circuit solution** | The physical answer at **one frequency**. Given complete inputs, `circuit.ts` calculates cone/port motion, acoustic output, impedance, phase, and related complex values for that frequency. |
| **Sweep** | Calls the circuit solution repeatedly over a frequency grid and collects the results into curves. |
| **Engine** | The public façade. It exposes solver, circuit-facing, sweep, air, and alignment operations. It contains no second copy of the maths. |
| **Domain** | Owns the project record and maps engine values/issues to fields and provenance. |
| **Hook/UI** | Displays values and diagnostics. It does not calculate or diagnose. |

## Calculatin Owners

| Calculation | Owner | Output |
|---|---|---|
| Driver T/S derivation | `engine/solver.ts` | solved driver values + driver issues |
| Sealed alignment | `engine/boxDesign.ts` through `Engine` | target-Qtc options, Vb, Qtc, closest option, EBP suitability |
| Vented alignment/port | `engine/boxDesign.ts` through `Engine` | Fb, vent length, reachable/unreachable issue |
| Passive-radiator tuning | `engine/boxDesign.ts`/`engine/solver.ts` through `Engine` | Fp, added mass, reachability issue |
| Box parameter validation | `engine/params.ts` through `Engine` | box prerequisite issues |
| Air properties | `engine/air.ts` through `Engine` | `rho`, `c`, environment issues |
| One-frequency physical response | `engine/circuit.ts` | one `Solution` at frequency `f` |
| Frequency response curves | `engine/sweep.ts` | curves + sweep issues/prerequisite references |
| Public access | `engine/Engine.ts` | the only calculation façade |

## Data Flow

```text
driver record ──> driver solver ──> solved driver values/issues ──┐
                                                                   │
box record ─────> box solver ─────> box values/issues ─────────────┤
                                                                   ├─> circuit at f
signal record ──> signal resolver ─> signal values/issues ─────────┤       │
                                                                   │       ▼
environment ────────> rho/c/issues ──────────────────┘   sweep curves/issues

The sweep may say which upstream fields block a curve. It does not copy those upstream DQ
messages into the sweep issue list.

}
```

```ts
type DriverIssue =
  | {
    adonly kind: 'missing-dependencies';
      readonly target: DriverQuantityName;

    }
  | {
      readonly kind: 'inconsistent-inputs';

      readonly actual: number;
      readonly relative: number;
    };

  readonly formula: string;
  readonly required: readonly DriverQuantityName[];
  readonly missing: readonly DriverQuantityName[];
}
```

Multiple routes are explicit. For example:

```text
Cms <- Vas + Sd + air
Cms <- Fs + Mms
```

If neither route is complete, the issue lists both routes and their missing fields. If both are
complete and disagree, the issue reports the contradiction and the declared route precedence.

## Diagnostic Channels

| Channel | Owns | Projected to |
|---|---|---|
| Driver | missing/inconsistent `Fs`, `Vas`, `Qts`, `Re`, `Pe`, `Xmax`, etc. | Driver cells / Driver-tab DQ |
| Box | missing/inconsistent `Vb`, `Vf`, `Fb`, vent geometry, PR mass/tuning, topology | Box/Vent/PR cells |

```

```

## Solver Nodes

These are separate solver nodes with the same result discipline. They are not separate copies of
the physics engine and they do not call the UI.

### Driver T/S Solver

**Input:** entered driver quantities,including provenance-independent numeric values such as
`Fs`, `Qes`, `Qms`, `Qts`, `Vas`, `Sd`, `Cms`, `Mms`, `Re`, `BL`, and geometry fields.

**Output:** all quantities derivable from the entered values, plus `DriverIssue[]`.

**Examples:**

- `Qts` from `Qes + Qms`.
- `Cms` from `Vas + Sd + air` or from `Fs + Mms`.
- `Fs` from `Mms + Cms`, `Rme + Qes + Mms`, or `EBP + Qes`.
- `Vas` from `Cms + Sd + air`.

If no route is complete, the output names every blocked route. If complete routes disagree, the
output reports the contradiction using the engine's declared route precedence.

### Sealed Alignment Solver

**Input:** driver `Qts`, `Vas`, target numeric `Qtc`, or driver `Qts`, `Vas`, and sealed `Vb`.

**Output:** calculated `Vb` or calculated `Qtc`, closest WinISD alignment option, and an
unreachable/missing-input issue where appropriate.

The WinISD sealed menu is nine target values:

```text
0.500 Critically damped
0.577 Max flat delay response
0.707 Max flat amplitude response
0.800 Equal ripple response
0.900 Equal ripple response
1.000 Equal ripple response
1.100 Equal ripple response
1.200 Equal ripple response
1.500 Equal ripple response
```

The labels are UI-facing names, but the engine owns the immutable numeric catalog and the mapping.
They are not separate Bessel, Butterworth, or Chebyshev implementations.

### Vented Alignment and Port Solver

**Input:** driver parameters, selected vented alignment, `Vb`, `Fb`, vent area/diameter, and end
correction.

**Output:** alignment `Vb/Fb`, physical vent length, achieved tuning, and box/vent issues.

The vent solver owns the inverse pair:

```text
Fb + Vb + vent geometry -> vent length
vent length + Vb + vent geometry -> Fb
```

An unreachable tuning reports a negative/unbuildable length as a box/vent issue. It does not become
a generic chart error.

### Passive-Radiator Solver

**Input:** PR parameters, `Vb`, target tuning, and added mass.

**Output:** target tuning, required added mass, system tuning, and PR-specific issues.

Negative required added mass means the target is above the bare-radiator ceiling. That is a PR
issue attached to the target/mass relation, not a sweep issue.

### Box-Parameter Solver

**Input:** active topology and its required chamber/port/PR fields.

**Output:** topology-specific box parameters and missing/invalid box issues.

It owns checks such as missing `Vb`, missing `Vf`, missing vent area, and missing PR compliance.
The sweep consumes the validated result; it does not repeat these checks.

### Signal Resolver

**Input:** project power, voltage, driver resistance, driver count, wiring, and series resistance.

**Output:** the drive value used by the circuit and signal issues.

The established 1 W project reference is a valid project input. Missing `Re` or an inconsistent
power/voltage pair is a signal issue. The circuit never guesses a signal value.

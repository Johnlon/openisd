# Testing Fixtures Doctrine

## Anti-Pattern: Hand-Cranked Static Fixtures
Never commit hand-cranked JSON or `.owpr` files (like a static `sample-project.owpr`) as test fixtures.
Static fixtures inevitably drift from the app's real behaviour. When the app's domain logic changes (e.g., adding a new physical default like `alfaVC` or `tuning_hz`), the static fixture masks the bug because tests are running against the hardcoded artifact rather than the real application output.

## The Solution: Programmatic Memoized Fixtures
Test fixtures representing "A User's Project" must be generated by the app's *actual* project creation logic (e.g., the New Project Wizard or `ProjectBuilder`), guaranteeing 100% structural fidelity.

To avoid the performance penalty of walking the UI wizard in every test's `beforeEach` hook, we use **memoized programmatic fixtures**:
1. A test setup helper (like `getWizardProject(driver, boxType, volume)`) checks if a cached `.owpr` file exists in a temporary `.test-cache/` directory for those exact parameters.
2. If it exists, it injects it instantly via Playwright's `setInputFiles` (fast).
3. If it does not exist, the helper drives the app logic (in-memory or via UI automation) to synthesise the project, exports it, saves it to the temporary `.test-cache/` file, and then injects it.

This guarantees that the starting state for any test is mathematically identical to a project created by a user *today*, not a project created by a user 6 months ago. When domain rules change, developers simply clear the `.test-cache/` directory, forcing the test suite to regenerate perfectly accurate fixtures on the next run.

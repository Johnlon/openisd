## Duplicate-logic check on every pull request

`scripts/dupscan.mjs` runs in its own `dupscan` job of `.github/workflows/pr.yml` (pull request and merge queue), before and apart from anything of the change: jscpd and typescript come from the base commit's `package-lock.json` (`npm ci --ignore-scripts` in RUNNER_TEMP), the scanner is staged from the head commit beside them and run there, so a `node_modules` in the checkout is never loaded (T934 review 6), and the ratchet compares with the event's base sha (T934 review 5). It finds copies of code with jscpd (pinned devDependency) and lines that match the formula rules (driver-count scaling, resonance, dB, air, unit factors, maths in `packages/ui`), and exits 1 on any finding not listed in `scripts/dupscan-allow.json`. A new copy of a formula therefore fails the pull request until the copy is removed (call the engine instead); the list itself only shrinks (T934, below). Findings that existed on 18 Nov 2026 are the baseline, each with reason "baseline 2026-11-18 (QO946.c256)" (John, 18 Nov 2026, "yes" to making the scan a check on every pull request). Test: `bash scripts/test/dupscan.test.sh`.

`scripts/dupscan-allow.json` is a gate file (listed in `GATE_FILES` in `land.conf`, John 18 Nov 2026, board item QO948: a pull request that changes it is refused unless its task has `gates_approved: QO<n>` for a board item John answered): a key added to it needs a `reason` that quotes a John ruling. Agents never add keys on their own and never regenerate it with `--write-baseline` (standing rule "No agent weakens anything on its own"). A key is never removed. When a copy is consolidated into the engine, its entry stays and is marked resolved: `"resolved": true, "resolved_to": "<engine file>:<function>", "resolved_by": "<task id>", "ruling": "QO949"` (John, QO949, 18 Nov 2026: "old entries stay, marked 'resolved, resolved to <engine function> by T902'; a resolved copy that reappears fails; T902 and future consolidations recorded so"). A resolved key never allows its copy: if it reappears the check fails and names the function to call. An allowed entry whose copy is gone fails the check until it is marked resolved (T911).

Homes and the ratchet (T934; John, 19 Nov 2026: "why wasn't the consolidation finished - our guard rail isn't working / remove the dupe and fix the guardrail"). Each kind of sum names its home in `scripts/dupscan-homes.json`: one engine declaration (`file:name`, a function, const or class member; never a whole file), found by its exact name with the TypeScript parser. For example every scaling by the driver count lives in `engine/array/driverWiring.ts`'s `combinedOfN`, `eachOfN`, `oneBoxOfN` and `driverDrive`, and air compliance in `engine/air.ts`'s `airCompliance`. A line whose every match lies inside its kind's home declaration is not a copy, so moving a sum into its home needs no list change; the same text anywhere else, code after the home's closing brace included, fails and names the home to call. A declared home must exist once and lie in `packages/design/engine/`. `scripts/dupscan-homes.json` and `scripts/dupscan.mjs` are gate files like the allow-list (`GATE_FILES` in `land.conf`), so a new home or a change to the check needs John's approval. The check compares the allow-list with the one on the base commit (`--base origin/main`) and the list only shrinks: a new entry, a raised count, a deleted entry, and a resolved entry made unresolved, replaced or rewritten (its `resolved_to`, `resolved_by` and `ruling` are history) all fail. The one exception is help text (QO950): a new entry whose reason starts "help text, no code" is accepted only when every match on its line lies inside a string or a comment, never for code and never for a jscpd copy. Keys leave comments out and keep literals exactly (strings, templates and regular expressions read by the TypeScript parser), and jscpd runs comment-insensitive (`--mode weak`), so rewording a comment, on one side of a copy or both, keeps a key. An entry re-keyed when a key's form changes names its old key in `"was"`: an unresolved base entry of the same rule and file (a copy: the same two files), claimed by that one entry, with no higher count, and the pair (old key, new key) must be in the reviewed re-key mapping `scripts/dupscan-rekey-T934.json` (`--rekey`, a gate file). Its `pairs` were made once from the base source (`--write-rekey` run on a checkout of the base, recorded in its `base`), so a line or copy changed since the base (a string's spaces, a copy grown over more shared code) is a different finding and never takes an allowance; a previous-form key the mapping moves allows nothing until its entry moves; its `hand_pairs` are pairs a person reviewed, each with its `why`. A `"was"` with no pair is refused. A resolved entry is recognised under either key form, before the allowances, so a consolidated copy that comes back is reported as such. A comment with no space around it (`f(/* note */x)`) keeps a key too. The pull request check runs the gate-approval check in its own job, `gate-approval` in `.github/workflows/pr.yml`, before and apart from anything of the change: it takes `scripts/ci/contract-from-base.sh` from the base commit (the event's base sha), which runs the base's `scripts/land/`, reading the change's `land.conf`, task files and file list as data, never sourcing them; a base without the runner fails closed, except the one pinned bootstrap base of the pull request that adds it (`BOOTSTRAP_BASE`), and there only when the runner and the checker scripts it runs have the sha256 sums recorded in `pr.yml` (`BOOTSTRAP_SHA256`). The checker lists every path the change touches with rename detection off (a renamed protected file counts by its old path too) and matches `GATE_FILES` patterns literally, never expanded by the shell; the base's `GATE_FILES` is read fail-closed (unreadable or empty refuses), and the checker's Python runs isolated (`python3 -I`), so no module in the checkout is imported. Where the board file is absent (a GitHub runner) `gates_approved` must still be a well-formed QO<n> (`scripts/land/check-task-contract.sh` header); where it is present, the item needs John's answer. Open owner decision (John's call, recorded in `tasks/T934.yml`): a pull_request run takes `pr.yml` from the change itself, so a change that edits `pr.yml` could drop that job; closing it needs a `pull_request_target` workflow or a repository rule requiring review of `.github/workflows/` changes. Until then every `pr.yml` change is reviewed by hand; the protected list (`GATE_FILES`) is read from the base revision's `land.conf` as well as the proposed one, and `.github/workflows/pr.yml`, the re-key mapping, the runner and the checker's scripts (`check-task-contract.sh`, `pr-task.sh`, `core/task.sh`, `task-gates/check-commit.sh`) are on it. T934 took the open entries from 248 to 204: 44 marked resolved, 28 because the code now calls an engine or shared function (`combinedOfN`, `eachOfN`, `oneBoxOfN`, `airCompliance`, `perCoilResistanceFactor`, and in `engine/boxes/port.ts` `tunedChamber`, `winisdLossyVentedChamber`, `winisdLossyChambers` and `seriesChambersWithLeak` for the band-pass chambers) and 16 because the line already was its kind's home; 70 entries were re-keyed with `"was"`: 69 as the base-source mapping pairs them, one (the AbcBox/Bandpass6Box class preamble, which the chamber-tuning consolidation ran on into) as a hand-reviewed pair. Switching jscpd to comment-insensitive mode showed six more copies (help panel Differences link, saved-library repo writes, PR box and vented chamber field types, file-format helpers, sync Lamport choice, mobile Advanced tab air fields); each now uses one shared function or type instead of being listed.
